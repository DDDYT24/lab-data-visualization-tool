## Purpose

> 首轮路线分析和已确认业务决策已固化在 [`DATABASE_DESIGN.md`](DATABASE_DESIGN.md)。
> 本文件继续作为数据库设计与实施流程约束。

本文件只负责指导 LabViz 的数据库与数据存储架构设计。

产品需求以 `prd.md` 为准，项目架构和现有接口以 `PROJECT_PLAN.md` 为准，未完成及延期工作以 `TODO.md` 为准。本文件不重复这些内容。

目标是建立一套能够支持以下能力的数据体系：

- 实验数据来源追溯
- 原始数据安全保留
- 数据处理版本管理
- 分析结果复现
- 可视化配置演进
- 本地与云端扩展
- 长期维护和数据库迁移

当前 FastAPI 和 SQLite 实现仅作为现有合约与测试参考，不代表生产数据库方案已经确定。

不得把现有参考实现自动升级为生产方案。

## Seven-Step Database Process

### 1. 从现有业务流程提取核心数据对象

根据代码和现有前端闭环识别真正需要持久化的数据对象。

重点分析但不要机械建表：

- User
- Project
- Experiment
- ExperimentRun
- SourceFile
- Dataset
- DatasetVersion
- CleaningDecision
- ProcessingRun
- ChartSpec
- Export
- ShareLink

说明每个对象：

- 来源
- 用途
- 生命周期
- 是否需要持久化
- 是否属于原始数据或派生数据
- 是否需要版本管理

不要按照页面数量设计数据表。

### 2. 明确关系、所有权和生命周期

分析对象之间的关系，并回答：

- 项目、实验和实验运行如何组织
- 原始文件属于哪个对象
- 一个文件能否产生多个数据集版本
- 清洗决策如何关联原始数据
- 处理结果如何记录输入、参数和输出
- 图表配置绑定哪个数据版本
- 分享链接可以访问哪些内容
- 临时项目、已保存项目和本地项目如何区分
- 删除、过期和恢复分别如何处理

优先输出领域模型和 Mermaid ER 图，不要直接生成 SQL。

### 3. 推荐最合适的数据库搭建路线

根据现有代码和真实使用方式，比较至少两种可行路线。

分析因素包括：

- 网站优先还是本地优先
- 单用户还是多用户
- 当前文件大小和未来增长
- 原始文件、结构化数据和派生结果的存储方式
- 查询、筛选、图表和导出需求
- 临时数据过期规则
- 并发、权限、备份和恢复
- 当前部署复杂度
- 未来 Windows 本地模式的兼容性

可以评估但不要默认选择：

- SQLite
- PostgreSQL
- DuckDB
- Parquet
- 本地文件系统
- S3 或兼容对象存储
- TimescaleDB
- Redis

每条路线需要说明：

- 组件职责
- 与当前项目的适配度
- 开发和部署成本
- 运维复杂度
- 扩展能力
- 当前是否过度设计
- 后续升级路径

推荐满足当前需求的最小复杂度方案。

### 4. 设计数据库和存储结构

路线确认后再设计 Schema。

设计必须保证：

- 原始文件原则上不可覆盖
- 原始数据与处理后数据分离
- 每次处理记录输入版本、处理参数、代码或算法版本和输出版本
- 清洗行为可以撤销和追溯
- `ChartSpec` 绑定明确的数据版本
- 大型文件是否进入数据库由实际规模决定
- 文件内容与数据库元数据的职责清晰

遵循三大范式，但避免为了范式过度拆表。

任何反范式、冗余字段、缓存或预计算结果都必须说明理由和一致性维护方式。

### 5. 统一数据规范

设计时明确：

- 表名和字段名规范
- 主键策略
- UTC 时间策略
- 外键、唯一约束和检查约束
- 数据版本字段
- 软删除和物理删除的适用范围
- 文件路径、对象键和 SHA-256 校验
- 单位、数值精度和缺失值规则
- JSON / JSONB 的使用边界
- 与实际查询对应的索引

必须区分：

- Database Entity
- Domain Model
- API DTO
- `ProjectSpec`
- `ChartSpec`
- 前端 View Model

前端不得直接依赖数据库 Schema。

### 6. 保存设计并进行版本管理

正式建表前，至少保存：

- 数据库路线及选择理由
- 领域模型
- Mermaid ER 图
- Schema 草案
- 数据字典
- Migration 方案
- 测试数据方案
- 备份和回滚方案

数据库结构变化必须通过 Migration 管理并提交 Git。

不得通过手工修改生产数据库或覆盖单一 `schema.sql` 来维护结构。

### 7. 制定实施和验证计划

按照最小风险顺序规划：

1. 确认生产数据库和存储路线
2. 配置数据库访问与 Migration
3. 建立核心元数据模型
4. 使用测试数据验证关系与约束
5. 接入原始文件和完整性校验
6. 接入 Dataset、处理记录和版本关系
7. 接入 `ProjectSpec` 和 `ChartSpec` 持久化
8. 接入历史、分享、过期和删除机制
9. 开发或调整业务接口
10. 替换参考实现中的临时存储
11. 验证追溯、复现、备份和关键查询性能

先打通基础存储闭环，再开发高级查询、缓存或分析优化。

## Required First Output

第一次执行本文件时，只输出：

1. 已读取的相关代码和文档
2. 当前数据流与存储现状
3. 已确定事实和待确认问题
4. 核心领域对象
5. 至少两种数据库路线对比
6. 推荐路线及理由
7. 初步领域关系
8. 分阶段实施计划
