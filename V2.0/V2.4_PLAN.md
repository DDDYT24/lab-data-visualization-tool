## 1. Why V2.4

V2.3 left two chart pipelines side by side:

- **Research charts** compute all geometry on the server (points with jitter, pair segments,
  KDE grids, group summaries). The browser shows a PNG and has no interaction. Only the y axis
  is left to Matplotlib's autoscale.
- **Composed boards** recover mark positions after rendering (`scene_json` schemaVersion 2) so
  the inspector can hit-test the PNG.
- **Classic charts** are computed twice: `web/src/components/common/chart-option.ts` builds the ECharts view
  from preview rows and `/analysis`, while `api/labviz_api/processing.py` renders the export
  separately. The two sides have different axis rules, which is the source of every
  preview-versus-export mismatch so far.

V2.4 makes the research approach the only one: the server decides every number that is drawn,
one plan describes the chart, and both renderers draw only that plan. No new chart families are
added before S3 lands, because each one would otherwise be implemented twice.

### 3.2 RenderPlan v1 as built in S3a

- **Shape:** `schemaVersion: 1`, `contract: "render-plan-v1"`, `planHash`, `source` (chart
  kind, `resultSha256`, algorithm version), `rendering` (point rendering, rasterization),
  `panels[]` (id, title, legend, `axes.x` / `axes.y`, `marks[]`) and `disclosures[]`.
- **Marks:** `points`, `segments`, `violin`, `summary`. Each carries `id` and `group`; every
  mark except `summary` carries `sourceRefs` (observation ids; pairs of ids for segments).
  Marks are drawn in list order: segments or violins, then points, then summaries.
- **Axis rule `nice-1-2-5-v1`:** the domain is the data range ± 5 % (Matplotlib's default
  margin), and the ticks use the smallest 1/2/5×10^k step that gives ≤ 6 ticks inside the
  domain. Category axes use the positions Matplotlib already used, for example
  (−0.65, n − 0.35).
- **Hash:** `planHash` is the SHA-256 of the canonical JSON of the plan without the hash.
  Colour and grayscale changes produce a different hash.
- **Contract source:** the Pydantic model in `render_plan.py` owns the schema.
  `contracts/render-plan-v1.schema.json` is generated from it, and the frontend builds its
  validator from that file with `z.fromJSONSchema`.

## 4. Outside V2.4 and not to do

**Moved to later stages:**
- **S4:** log axes, manual domains, annotations and panels 5–6. S3 plans can already express
  `scale` and `domain`, but research charts use only `linear` / `category`.
- **S5:** compute cache, DuckDB, `/api/v2` and capabilities.

**Not to do during V2.4:**
- add chart kinds before S3;
- keep any frontend statistics fallback;
- put new binaries into SQLite;
- introduce Redis, Celery or Kafka (`api/tests/test_architecture_boundaries.py` rejects them);
- start cloud or macOS/Linux packaging first;
- relax release discipline (hash binding, offline acceptance, owner testimony kept apart from
  automated evidence).

**Not replaced by any stage:** native, device and owner acceptance for V2.3 (desktop parts 2–4
under `desktop/`). Automated runs do not sign off native behaviour.
